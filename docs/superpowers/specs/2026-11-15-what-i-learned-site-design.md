# 学んだことの記録サイト 設計

日付: 2026-11-15
リポジトリ: `KJMAN678/what_i_learned`（現在は空）
公開先: `https://kjman678.github.io/what_i_learned/`

## 意図と背景

- **主目的:** 自分が後で見返して調べ直すための記録。
- **副目的:** 人に「自分はこんなことを学んでいる」と紹介する。
- 書く手間が少ないことと、後で探せることを最優先にする。

## ゴール

1. 1日分の記録を Markdown ファイル1つで書ける。必須の項目はタグだけ。
2. 一覧ページ（年度でグルーピング）で記録を見渡せる。
3. 記録ごとに詳細ページがある（1日 = 1記事 = 1ページ）。
4. タグで絞り込める。全文検索で探せる。
5. 「この1ヶ月」ページで、直近30日に何を学んだかを可視化する。

## 非ゴール

- コメント、CMS、RSS、アクセス解析、多言語対応、下書き機能は作らない。
- 1テーマ = 1ページの構成にはしない。テーマ単位では追わない。
- 「この1ヶ月」ページに、タグの登場回数と記録日数以外の指標は載せない。

## アンチゴール

- 書くのが面倒になること。frontmatter の必須項目を増やす、厳しい書式を課す、ビルドが通らなくなる、といった形で記録の手間を増やしたら失敗とみなす。

## 制約

- 公開サイトなので、書いた内容はすべて公開される（リポジトリも Pages も公開前提）。
- 年度は4月始まりとして扱う（2026年11月は「2026年度」、2026年1月は「2025年度」）。
- 記録はローカルで書く。Claude Code と壁打ちしながら文章を作り、エディタか Claude Code から push する。Web 画面やスマホからは書かない。
- 記録の形はユーザーの例に合わせる。1日の中に「学習」「気になった技術情報」などの見出しと、入れ子の箇条書きが入る。

## 検討した方法

| 案 | 内容 | 得意 | 苦手 |
|---|---|---|---|
| **A. Astro + Pagefind（採用）** | Markdown を Node で静的サイト化し、GitHub Actions で公開 | 年度別一覧、タグ、全文検索、集計を自由に作れる | Node と Actions の初期設定が要る |
| B. Jekyll | GitHub Pages 標準のビルド。Actions 不要 | 設定が最小 | 全文検索は別途 JS が必要。集計が書きづらい。ローカル確認に Ruby が要る |
| C. MkDocs Material | 検索とタグが最初から付く | 検索とタグが最速 | 年度グルーピングと1ヶ月ページが型に合わない |

ユーザーが A を選んだ。理由: 年度グルーピング、タグ集計、1ヶ月ページがすべて自作の画面で、Astro なら普通に書けるため。

## 決まっていること（ユーザーが決めた内容）

- 1記事 = 1日。
- 一覧は年度でグルーピングする。
- タグと検索で探せる。
- 「この1ヶ月」の可視化ページを作る（可能なら）。
- 記録の例（2026/11/15）の書き方を、そのまま書けるようにする。

## 設計（ビルダーの判断を含む。★は私の判断）

### 記録ファイル

- 置き場所: リポジトリ直下の `records/YYYY-MM-DD.md`。★
- ファイル名が日付になる。日付を frontmatter には書かない。
- frontmatter は `tags`（文字列の配列）が必須。★
- `summary`（一言）は任意。あれば一覧に表示する。★
- 本文は自由な Markdown。入れ子の箇条書きがそのまま描画される。
- 書式チェックは厳しくする（ユーザーの書き方がローカルなので）。次の場合はビルドを失敗させる。
  - `tags` がない、または空。
  - ファイル名が `YYYY-MM-DD.md` でない、または実在しない日付。
  - frontmatter が壊れている。
- push 前に気づけるよう、`npm run check` で同じチェックを手元で実行できるようにする。
- 記録の書式（置き場所、frontmatter、本文の型）を `CLAUDE.md` に短く書いておく。Claude Code が記録を作るときに、そのとおりに書けるようにするため。★

```markdown
---
tags: [MCP, Docker, AWS, FBC]
summary: MCP本を読んだ / 猫見守りの開発環境を整えた
---

- 学習
  - MCPサーバー開発大全 をざっと読んだ
    - 〜〜が気になった
- 気になった技術情報
  - 〜〜〜の記事
    - 〜〜〜をやってみたい
```

### ページ

| URL | 内容 |
|---|---|
| `/` | 一覧。年度ごとの見出しの下に、新しい順で日付・タグ・summary を並べる。検索ボックスとタグ一覧を置く |
| `/records/YYYY-MM-DD/` | 詳細。日付を見出しに、タグ（タグページへのリンク）、本文を表示する |
| `/tags/<tag>/` | そのタグが付いた記録の一覧（年度でグルーピング） ★ |
| `/recent/` | 直近30日のタグ登場回数（多い順）と、記録した日数（「N日 / 30日」） ★ |

### 検索とタグ

- 全文検索は Pagefind。ビルド後に索引を作り、一覧ページの検索ボックスで使う。サーバーは不要。
- Pagefind の索引はビルド後にできるため、`astro dev` では検索が動かない。検索の確認は `build` + `preview` で行う。
- タグ絞り込みは `/tags/<tag>/` の静的ページで行う。JS は不要。★

### 「この1ヶ月」ページ

- 範囲は「暦月」ではなく、今日から遡る30日間。★
- 閲覧時の日付で集計するため、ビルド時に全記録の `{日付, タグ}` を JSON で埋め込み、ブラウザ側の JS で集計する。★ 理由: サイトは push したときしか再ビルドされず、ビルド時に集計すると数日記録しない間に古い数字が出続けるため。

### 年度

- 年度 = 4月始まり。4〜12月はその年、1〜3月は前年。★
- 年度の計算と30日集計は、小さな関数に切り出し、単体テストを1本置く。★

### 公開

- GitHub Actions（`withastro/action` と `actions/deploy-pages`）で、`main` への push 時にビルドして公開する。
- `astro.config` の `site` は `https://kjman678.github.io`、`base` は `/what_i_learned`。
- 初回だけ、ユーザーがリポジトリの Settings → Pages で Source を「GitHub Actions」に切り替える必要がある。

### 見た目

- フレームワークや UI ライブラリは使わず、素の CSS で作る。ライト/ダーク両対応。`lang="ja"`。★
- 凝らない。読みやすさ優先。

### 初期データ

- ユーザーが示した 2026/11/15 の例を最初の記録として入れる。★ 「〜〜」の部分は後でユーザーが書き換える。

## ビルダーに任せること

- Astro のバージョン、ディレクトリ構成、Content Collections の細かな書き方。
- CSS の細部、タグ一覧の見せ方、ファイルの分け方。
- テストランナーの選定（Node 標準のテストで足りるなら追加依存は入れない）。

## 検証の目安

- `build` が通り、`preview` で `/`、詳細、`/tags/...`、`/recent/` が開ける。
- 検索ボックスに記録内の語を入れるとヒットする。
- 年度の境界（3月31日と4月1日）と30日集計のテストが通る。
- Actions が成功し、`https://kjman678.github.io/what_i_learned/` で表示される。
