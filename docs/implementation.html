1. 全体像

ログを書いてから公開されるまでの流れです。どの段階で失敗しても、それ以降には進みません。公開に失敗した場合、サイトは前回の内容のままです。

① 書くcontent/logs/YYYY-MM-DD.md を作る
→
② コミットpre-commit が秘密情報・.env・ログ形式を検査
→
③ pushmain への push で GitHub Actions が起動
→
④ build ジョブpytest → build.sh（検証 → Zensical ビルド）
→
⑤ deploy ジョブsite/ を GitHub Pages へ

サイト生成には Zensical（Material for MkDocs の後継）を使います。Zensical の設定（zensical.toml）は content/ を入力、site/ を出力とし、ログは blog プラグインではなく通常のページとして 1 ファイル = 1 ページで出力します（blog プラグインは frontmatter に date を要求し、書く手間が増えるため）。

3. ログ形式

日付はファイル名から取り、frontmatter の必須項目は tags だけです。書く手間を最小にするための設計です。

---
tags:
  - 技術書
summary: 技術書を読んだ      # 任意・1 行
---

## データ指向アプリケーションデザイン 第2版

- 1章を読んだ
項目ルール
ファイル名YYYY-MM-DD.md で、暦上存在する日付（2026-02-30.md は不可）
文字コードUTF-8
tags必須。空でない文字列のリスト。tags: aws のような単一文字列は不可
summary任意。改行を含まない文字列
その他のキー無視する（エラーにしない）

4. wil.records：パースと検証

wil.records はログ形式を定義する唯一のモジュールです。一覧ページや MCP など後続の機能は、パーサを再実装せずにここを使います。

データモデル

@dataclass(frozen=True)
class Record:
    date: date              # ファイル名から
    path: Path
    url_path: str           # "logs/2026-11-23/"
    tags: tuple[str, ...]
    summary: str | None
    body: str               # frontmatter を除いた本文
    sections: tuple[Section, ...]   # 見出しで区切った本文

@dataclass(frozen=True)
class Section:
    level: int   # 0 = 最初の見出しより前, 1..6 = 見出しの階層
    title: str
    body: str

どちらも frozen=True で不変にしてあり、読み取った後に書き換えられることはありません。

parse_record(path)：1 ファイルを読む

上から順に検査し、最初に見つかった問題を RecordError(path, reason) として投げます。

  1. ファイル名が \d{4}-\d{2}-\d{2}\.md に一致するか
  2. date.fromisoformat で実在する日付か
  3. UTF-8 として読めるか（読めない・I/O エラーも RecordError に変換）
  4. 先頭行と 2 つ目の --- で frontmatter を切り出し、yaml.safe_load で mapping として読めるか
  5. tags・summary の型と値
yaml.safe_load を使うため、YAML の任意オブジェクト生成は行われません。

_split_sections(body)：見出しで本文を区切る

ATX 見出し（#〜######）の行で本文を Section に分けます。ポイントは 2 つです。

  • コードフェンスの中は見出しとみなさない。 ``` や ~~~ で開いたフェンスは、同じ記号で同じ長さ以上の行でだけ閉じます（CommonMark と同じ規則）。シェルのコメント # ... が見出しに化けるのを防ぎます。
  • 見出し末尾の閉じ # は除く。 ## タイトル ## の title は タイトル です。

最初の見出しより前に空白以外の本文があれば、level=0 のセクションとして残します。

load_records(content_dir)：全ログを読む

content/logs/*.md をすべて読み、日付の昇順で返します。1 件でも不正があれば、全件のエラーを集めて RecordsInvalid を投げます。1 件ずつ直して再実行する手間を省くためです。ドットで始まるファイルは対象外です。

check_paths(paths)：公開してよいファイルか

pre-commit とビルド前検証の両方から呼ばれる、公開事故防止の中心です。

# content からの相対 POSIX パスに対する正規表現（fullmatch）
ALLOWED_PATTERNS = (r"index\.md", r"logs/\d{4}-\d{2}-\d{2}\.md")
パスの状態結果
content/ の外対象外（スキップ）
ドットファイル・ドットディレクトリ配下対象外（Zensical も公開しない）
パスの途中のどこかがシンボリックリンクエラー
存在しない・ディレクトリ対象外（削除のコミットなど）
ALLOWED_PATTERNS に一致しないエラー（許可リスト方式）
ログのパターンに一致parse_record で形式も検査
位置の判定に Path.resolve() ではなく os.path.abspath を使っているのは意図的です。resolve はリンクをたどるため、content/ 内のリンクの実体が外にあると「公開ディレクトリ外」と判定され、素通りしてしまいます。

main()：CLI

uv run python -m wil.records                 # content/ 全体を検査
uv run python -m wil.records path1 path2     # 指定ファイルだけ（pre-commit から）

エラーは path: reason 形式で標準エラーに出し、終了コード 1 を返します。引数なしで content/ が見つからないとき（リポジトリルート以外で実行したとき）も失敗にします。何も検査せずに成功するのを防ぐためです。

5. 公開事故を防ぐ多層の検査

リポジトリもサイトも公開なので、意図しないファイルが出ないよう、複数の段階で同じ方向の検査を重ねています。

.gitignore — site/、キャッシュ、.venv/、.env・.env.* などをそもそも追跡しない
pre-commit — gitleaks（秘密情報）、detect-private-key、500KB 超のファイル禁止、.env 系の禁止、content/ 配下を wil.records で検査、ruff
build.sh の検証段 — Zensical の前に content/ 全体を wil.records で検査。pre-commit を通さずに入ったファイルもここで止まる
Zensical --strict — リンク切れなどの警告をエラーにする
CI の権限分離 — 依存を実行する build ジョブは Pages への書き込み権限を持たない

6. ビルド手順 build.sh

#!/bin/sh
set -eu

# 1. 検証: 公開ディレクトリ全体
uv run python -m wil.records

# 2. 生成
# --- pre-build generation: 後続 spec がここに生成コマンドを追加する ---

# 3. ビルド
uv run zensical build --clean --strict

# 4. 付録: この解説ページ
cp docs/implementation.html site/implementation.html
  • 手元と CI が同じスクリプトを使うので、「手元では通るが CI で落ちる」差が生まれにくい
  • set -eu で、どれかが失敗した時点で止まる
  • 「2. 生成」は今は空です。一覧ページなどを Markdown として生成するコマンドを後続 spec がここに足します（Zensical は任意のプラグインを使えないため、ビルド前生成で補う方針）
  • 「4. 付録」は、このページを content/ の許可リストを広げずに公開するための段です。--clean で site/ が作り直された後にコピーします

7. 公開ワークフロー deploy.yml

main への push（または手動実行）で動きます。2 つのジョブに分かれています。

ジョブ権限やること
buildcontents: readcheckout → uv のセットアップ → uv sync --frozen → pytest → build.sh → site/ を成果物としてアップロード
deploypages: write, id-token: write成果物を GitHub Pages に公開。リポジトリのコードも依存も実行しない

サプライチェーン対策

  • ワークフロー全体の既定権限は permissions: {}（なし）。必要な権限だけをジョブごとに付与
  • Actions はタグではなくコミット SHA で固定（タグの付け替えで中身が変わる攻撃を防ぐ）。更新は Dependabot に任せる
  • persist-credentials: false で、checkout 後にトークンをディスクに残さない
  • uv のバージョンを固定し、uv sync --frozen でロックファイルどおりの依存だけを入れる。キャッシュは無効
  • 依存を実行するジョブ（build）と、書き込み権限を持つジョブ（deploy）を分ける
  • concurrency: pages・cancel-in-progress: false で、デプロイが途中で打ち切られない

8. テスト

tests/test_records.py は wil.records を対象にし、CI では build の前に必ず実行されます。主な観点は次のとおりです。

観点例
正常系正しいログの読み取り、summary 省略、未知キーの無視
ファイル名・日付・文字コード不正なファイル名、存在しない日付、UTF-8 以外
frontmatter区切りなし、YAML 不正、mapping 以外、tags・summary の型
見出しの分割フェンス内の #、フェンスの閉じ方、閉じ # の除去、level 0
公開ファイルの検査許可外ファイル、シンボリックリンク（実体が外・ディレクトリがリンク）、ドットファイル、削除済み
CLI終了コード、引数なしで全体検査、content/ がないと失敗、実際の content/ が通ること

9. 後続 spec の差し込み点

01 は、後続の機能が既存コードを書き換えずに乗れるよう、差し込み点を用意しています。

差し込み点使い方
load_records() と Record一覧・タイムライン・MCP などがログを読むときの唯一の入口
Record.sections見出し単位で本文を扱いたい機能（知見の検索など）向け
ALLOWED_PATTERNS生成ページの置き場所を許可するときに 1 行追加する
build.sh の「2. 生成」ビルド前に Markdown を生成するコマンドを追加する
